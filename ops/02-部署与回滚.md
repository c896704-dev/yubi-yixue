# 02 · 部署与回滚

## 部署链路

```
本地改代码
   ↓
① commit + push 到 GitHub          （终端面板或沙箱，见 01 的 git 一节）
   ↓
② rsync 源码到服务器                （终端面板，沙箱连不上 22 端口）
   ↓
③ 服务器上 npm run build            （前端产物 → dist/，nginx 立即生效）
   ↓
④ pm2 restart yubi-yixue            （仅当 server/ 有改动）
   ↓
⑤ 验证（见 03）
```

服务器信息：`root@115.190.56.178`，应用目录 `/var/www/yubi-yixue`，
pm2 进程名 `yubi-yixue`（cluster，跑 `server/index.js`，端口 3002），
nginx 静态服务 `dist/`、`/api` 反代 `127.0.0.1:3002`。

---

## 改了什么 → 要做什么

| 改动位置 | rsync | build | pm2 restart | nginx reload |
|----------|:-----:|:-----:|:-----------:|:------------:|
| `src/`（前端） | ✅ | ✅ | — | — |
| `src/report/*.css`、`src/index.css` | ✅ | ✅ | — | — |
| `server/`（后端） | ✅ | — | ✅ | — |
| `public/`（会拷进 dist） | ✅ | ✅ | — | — |
| `.env` | 单独改，不随 rsync（被 exclude） | — | ✅ 需要重启才读到新值 | — |
| `/etc/nginx/` | — | — | — | ✅ 见下 |

**只改注释也算前端改动**，但产物哈希通常不变，build 之后可以对比 hash 确认（没变就说明确实只动了注释）。

## rsync 的正确写法

```bash
rsync -rltz --no-owner --no-group --chmod=Du=rwx,Dgo=rx,Fu=rw,Fgo=r \
  -e "sshpass -p '***' ssh -o StrictHostKeyChecking=no" \
  --exclude node_modules --exclude .git --exclude dist --exclude .env \
  --exclude .DS_Store --exclude data --exclude .playwright-mcp --exclude wiki \
  ./ root@<host>:/var/www/yubi-yixue/
```

三条硬规矩，都是踩出来的：

1. **不要用 `-a`。** `-a` 会把 macOS 项目目录的 **700 权限和 uid** 一起同步过去，
   nginx worker 进不去 `/var/www/yubi-yixue` → **全站 404**（error.log 里是 `stat() failed 13 Permission denied`）。
   用 `-rltz --no-owner --no-group --chmod=...` 从源头规避，比事后 chmod 更稳。
2. **不要加 `--delete`。** 会删掉服务器特有的文件。
3. **显式 `--exclude dist`。** 不用本地构建产物覆盖服务器的 dist。

rsync 之后要兜底修一次权限，并**重新 build**（前端产物必须重生成）：

```bash
chmod 755 /var/www/yubi-yixue /var/www/yubi-yixue/dist
find /var/www/yubi-yixue/dist -type d -exec chmod 755 {} +
find /var/www/yubi-yixue/dist -type f -exec chmod 644 {} +
```

> `.env` 被 rsync 排除了，所以**服务器上的 `.env` 要单独改**（例如换模型名、换 key）。
> 改完必须 `pm2 restart` 才会被 dotenv 重新读到。

## 改 nginx 配置的安全流程

nginx 是生产配置，**改挂了整站就没了**。固定四步，别跳：

```bash
# 1) 备份
cp /etc/nginx/sites-available/yubi-yixue /root/backups/nginx-yubi-yixue-$(date +%Y%m%d-%H%M%S).conf

# 2) 改（改完 cat 一遍确认）

# 3) 先测语法 —— 这一步不通过就不要往下走
nginx -t

# 4) 通过了才 reload（reload 不断连接，restart 会断）
systemctl reload nginx
```

**回滚**：拿备份覆盖回去 → `nginx -t` → `systemctl reload nginx`。

> 建议把「改」这一步写成脚本 scp 过去执行，而不是在命令行里跟引号搏斗
> （中文、`${}`、括号组都会被终端面板的守卫拦下来，见 01）。

**改完要按内容验证，不要只看状态码** —— 理由见 03 开头的「软 404」。

## 备份位置约定

| 位置 | 内容 |
|------|------|
| `/root/backups/nginx-yubi-yixue-<时间戳>.conf` | 每次改 nginx 前的配置备份 |
| `/root/backups/yubi-yixue-<时间戳>.tar.gz` | 整站源码快照 |
| `/root/backups/fengshui.db` | ⚠️ 手工拷的库——**见下** |

### ⚠️ 数据库备份不能 `cp .db`

SQLite 跑在 WAL 模式下，**主文件在任意时刻都可能落后于逻辑数据库**
（生产实测：主文件 mtime 落后 WAL 约 4 小时，WAL 是主库的 81%）。

- `cp fengshui.db` → **静默丢掉 WAL 里的全部写入**
- 把 `.db` 和 `-wal` 分两次拷 → 两者不是一对可恢复的快照
  （WAL 头带 salt，必须与配对的 `.db` 严格匹配），**很可能根本恢复不了，而且出事前不会发现**

正确做法：

```bash
sqlite3 /var/www/yubi-yixue/server/data/fengshui.db ".backup /root/backups/fengshui-$(date +%F).db"
# 或 VACUUM INTO
```

备份完**立刻用 `PRAGMA quick_check` + 行数抽查验证能恢复**——没验证过的备份不算备份。
另外备份要和生产**异地**（现在同在 `/dev/vda2`，一次磁盘故障带走两者）。

## pm2 常用

```bash
pm2 status                                    # 状态、重启次数、内存
pm2 logs yubi-yixue --err --lines 50 --nostream   # 错误日志（排查必看）
pm2 logs yubi-yixue --out --lines 50 --nostream   # 输出日志（AI 调用结果在这）
pm2 restart yubi-yixue --update-env           # 改了 .env 要这样重启
```

**注意**：`pm2 logs` 不加 `--nostream` 会一直挂着（可以在终端面板里 Ctrl-C）。

`restarts` 计数**分不清「部署重启」和「崩溃重启」**，看到数字大不要直接当成不稳定。

## 一条经验

**上线前后各跑一次同样的检查，并且把结果记下来。**
没有「上线前」的基线，「上线后」的异常就看不出来——
比如 `POST /api/analyze/ai-report` 的 500，是在对比前后才确认它从 500 变成了 400。
