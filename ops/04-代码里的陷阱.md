# 04 · 代码里的陷阱

> 这里挑的是**改这个代码库时会咬你一口**的地方：看着没问题、编译不报错、数据也正常，
> 但结果是错的。按模块分组。
>
> 与 `wiki/问题修复记录.md` 的区别：那份记的是「已经修好的 bug」，
> 这份记的是「**再改这里时要注意什么**」。

## A. 报告层（`src/report/`）

### A1. `.report` 这个 container 不能丢

`src/report/report.css` 里**全部正文排版**——字号、行高、表格边框与内边距、表头底色、
引用块、标题样式——都挂在 `.report` 下面。

`ReportView` 渲染**字符串 body** 时会自动包一层 `<div className="report">`。
如果哪天这个包裹没了，症状会非常迷惑人：

- 表格**还在 DOM 里**（数量对得上），但退化成无边框无内边距的裸 `<table>`
- 字号回退到浏览器默认
- 看起来就是「表格没了、样式没了、字看不清」

**数据层完全正常，所以任何只查数据的核对都发现不了它。**

> 改 `ReportView` 的 body 渲染那几行之前，先确认这层包裹还在。

### A2. 行宽控制放在容器上，不要按元素卡 `em`

曾经用过 `.report :is(p,…) { max-width: 44em }`。15px 字号下那是 660px，
而卡片内宽有 841px → **正文右边永久空 180px**（AI 解读卡最明显）。
按元素卡的坏处是：卡片越宽空白越大，而且这一层完全看不见。

现在交给容器（`.site-container` 上限 1152px）。**别再给元素加 em 上限。**

### A3. 折叠章节的正文必须留在 DOM 里

`ReportView` 渲染 body 时**不用条件渲染**，只用 `.is-collapsed` 的 CSS 隐藏。

原因：`@media print` 无法让一段**根本没被渲染**的内容出现。
如果写成 `{open && <div>…}`，用户收起过的章节会**整章从 PDF 里消失**，
而屏幕上完全看不出异常。曾被这个坑到过一次。

### A4. 原生 `<details>` 无法用 CSS 强制展开

页内所有 `<details>`（方法论披露、晚子时口径对照）由 `ReportView` 的
`beforeprint` 监听器同步展开、`afterprint` 还原。

**新增任何 `<details>` 都不用另外处理**——只要它在这个 `ReportView` 的子树里。
但要注意：**用第三方「网页转 PDF」服务（不走浏览器打印）时会丢内容**，
因为那条路径不触发 `beforeprint`。这是已知边界。

### A5. AI 章节不占正文序号

`deriveChapterNums()` 对 `kind:'ai'` 返回空串。这是**故意**的：
AI 卡按设计不显示序号，若给它编号就会出现「导航说十二、卡上没有十二」。

### A6. `resolveChapters()` 的两处过滤必须在派生序号之前

```ts
spec.chapters
  .filter(c => !c.when || c.when(ctx))                    // ① 条件不满足 = 本章不存在
  .filter(c => c.kind !== 'ai' || Boolean(ctx.ai?.[c.id])) // ② 没有 AI 内容 = 整章跳过
// 然后才 deriveChapterNums
```

把过滤留到渲染时做，导航里会留下**点不开的幽灵条目**
（风水「楼盘位置分析」没有 AI 报告，就是这么暴露的）。

### A7. 加新板块时：`doc()` 与导出按钮必须同批交付

`exportDocx.ts` 在可见章节缺 `doc()` 时**直接抛错**（好设计：宁可不生成，也不悄悄少一章）。
但代价是——**给某板块加上导出按钮、却忘了补 `doc()`，用户会当场吃到异常。**

目前只有识人板块有 `doc()` 和导出按钮。其余板块**没有按钮**，所以按不到、也就看不到报错。

## B. 排盘与引擎口径

### B1. 切月有两套 API，差一个后缀就错一个月

```
lunar.getMonthInGanZhi()        → 按【自然日】切（交节当天 0 点即换月）
lunar.getMonthInGanZhiExact()   → 按【交节时刻】切
EightChar.getMonth()            → 同 Exact（八字引擎走这条）
```

实测 2026-08-07 10:00（立秋 19:42 才交节）：

```
getMonthInGanZhi()       = 丙申   ← 错一月
getMonthInGanZhiExact()  = 乙未   ← 对
EightChar.getMonth()     = 乙未   ← 对
```

**当前 `src/utils/ganzhi.ts:49`（`getJieQiInterval`）与
`src/features/divination/utils/meihua.ts:339`（`getLunarMonth`）用的仍是非 Exact 版**
——即六爻/梅花的**月建/月令/应期/卦气旺衰**在交节当天会错一个月，
且六爻页同一屏上「四柱」与「月建」会互相矛盾。

修法是两处各加一个 `Exact` 后缀。**改这里时注意两处都要改。**

### B2. `getSizhu` 是第二个排盘入口，而且丢了分钟

`src/utils/ganzhi.ts:21` 的 `getSizhu(y, mo, d, h)` **没有分钟参数**，
内部写死 `Solar.fromYmdHms(y, mo, d, h, 0, 0)`。

它被神煞页（`ShenShaPage.tsx`）与六爻页（`liuyao.ts`）各用一次。
于是**当交节时刻落在出生真太阳时同一小时内**，神煞页与八字页会给出不同的月柱。

它的月柱本身用的是 `EightChar.getMonth()`（精确），所以**与八字同源**——
问题只在分钟被丢弃。**别把它当成"另一套口径"去重构，它只差一个参数。**

### B3. 日柱的 `tenGod` 恒为字面量 `"日主"`，不是十神

`lunar-typescript` 的 `eightChar.getDayShiShenGan()` 对日柱返回 `"日主"`。

后果：`src/utils/analysis.ts` 里那段「配偶宫」判词

```ts
const god = result.bazi.day.tenGod          // 恒为 "日主"
if (god === '正官' || god === '正财') { … }  // 永不命中
else if (god === '偏官' || god === '偏财') { … } // 永不命中
else if (god === '比肩' || god === '劫财') { … } // 永不命中
```

**三个分支全是死代码**，正文恒为「配偶宫：日支 X（…），为日主。」——
语义空洞、语法还不通。改它**不触碰 AI 输入串**（不在 `buildBaziAiContext` 链路上）。

> 另外两处注释（`analysis.ts` 里）写的是「日柱十神恒为比肩」——那句话是**错的**，
> 是同一个认知错误的另一个投影。

### B4. 历法只认 `lunar-typescript`

干支、节气交节时刻、晚子时换日一律取自该库。
历史上手写的干支表与近似节气表**都引入过系统性错误**（详见 wiki）。
**不要新增手写历法表。**

### B5. 算「岁运 × 原局」不要复用 `getChongHeAnalysis`

`getChongHeAnalysis(year, month, day, hour)`（`chonghe.ts:397`）的语义是
**「这四支内部存在哪些关系」**，内部实现全是 `branches.includes(...)` 的**集合判定**，
柱位也被 `PillarName` 锁死在年月日时。

拿它算「大运/流年 vs 原局」会同时错三处：

- **重复计入**：把 natal 四支 + 三垣 + 运支揉成一个数组传进去，原局内部的关系会被再报一遍
  （报告里已经有一份了，每步大运再报一次）
- **假阳性**：自刑判定是 `branches.filter(x=>x===b).length >= 2` ——
  原局本来就双辰时，运支再来一个辰也算进"这一组"，实际上引没引动分不清
- **漏报**：位次（"冲的是哪个宫"）靠 `getPositions` 去重收集，无法表达"外部支冲了哪一个"

**要用 `relation.ts` 的三个扫描原语**：`scanBranchExt`(141) / `scanStemExt`(208) / `scanZhuExt`(235)
—— 它们只配 `(外部, 带标签目标)` 对，natal↔natal 绝不配对，从结构上杜绝上面三错。

> 关系表（六合/三合/六冲/六害/六破/三刑/自刑/干合/干冲）现在是 `relation.ts` 单一来源，
> `chonghe.ts` 反向 import。**加新关系时改 `relation.ts` 一处即可**，两套分析同时生效。

### B6. 大运的公历年不要自己反推

`BigFortune.startAge` 是**虚岁**，看着像能算：`birthYear + startAge - 1`。
**真太阳时的 `dayOffset` 会把起运基准日期推过元旦，这个式子就偏 1 年**
（晚子时出生、或生日贴近年初时踩中）。

库本身给了 `DaYun.getStartYear()/getEndYear()`，`bazi.ts:152` 已经透传成
`BigFortune.startYear/endYear`（`types.ts:34`，可选字段，向后兼容）。
**展示与计算一律用这两个字段**，别用虚岁反推。回归测试里有一条专门锁这个不变量：
所有大运的 `startYear - (startAge - 1)` 必须相等。

> 写引擎回归时至少覆盖这三类边界：**`dayOffset≠0` 的晚子时、立春前生日、原局重支**。
> 常规命例测不出上述漂移。

## C. AI 层

### C1. 提示词在客户端，不在 `server/`

**所有 AI 提示词都在 `src/utils/ai.ts`。** 在 `server/` 里 grep「古籍」是 0 命中——
那是必然的，**证明不了任何关于提示词的事**。（审查过程中有人正是这么误判的。）

### C2. 上游配置只有一处来源

`server/services/ai-config.js`。`routes/ai.js` 与 `services/ai-service.js` 都从它取。

**这是被教训出来的**：此前两处各写一套 baseUrl/model/URL 拼接，
于是「官方改一次模型名」要改两个地方，漏一处就只剩半边能用。

### C3. 模型名与推理型模型的 max_tokens

官方当前支持的模型名是 **`deepseek-flash`（推理型）与 `deepseek-v4-pro`**。
旧名 `deepseek-v4-flash` 已不在官方列表里（暂时仍能解析，属遗留别名）。

⚠️ **`deepseek-flash` 是推理型**：思维链（`reasoning_tokens`）**先占 `max_tokens` 额度**。
实测思维链可占输出额度的 75%、单次最高 93.5%。**给小了正文直接是空的。**
所以 `AI_MAX_TOKENS = 16384`，且 `aiFetch` 遇到「上游 200 但 content 为空」时会显式报错。

### C4. `getFengshuiReportPrompt(data)` 会解构 `undefined`

它第一行就 `const { orientation, … } = data`。传 `undefined` 进去抛 TypeError。
**调用方必须自己守**（`analyze.js` 里已加 400 校验）。

### C5. 同一记录的两条 AI 并发写会互相覆盖

识人板块现在**同时**跑两条 AI（识人解读 + 轨迹解读），各写各的字段。
如果沿用它原来的写法（读整行 → 改一个字段 → **整行** upsert 回服务端），就会出事：

- **写覆盖**：两条几乎同时完成时，后写的那条带着**自己读到的旧整行**，
  把对方刚写好的字段抹成 null
- **更阴的是读侧**：服务端 GET 若没有返回新列（`trajectory_insight`），
  客户端合并（`db.ts` 的 `getRenshiRecordsMerged`）会拿"服务端整行"盖本地 →
  **每次跨设备同步都在悄悄删掉本地刚写的那个字段**，而且因为服务端优先所以永远同步不回来

**现在的写法**（改这块时别退回去）：

| 位置 | 做法 |
|------|------|
| 服务端 | `PATCH /api/renshi/records/:id/ai`，`AI_COLUMN` 白名单映射列名，**只 UPDATE 单列**（`server/routes/renshi.js:41`） |
| 服务端 POST | 两个 AI 列用 `COALESCE`，请求没带就不覆盖 |
| 服务端 GET | **必须**返回 `trajectoryInsight` |
| 客户端 | `updateRenshiAi` / `updateRenshiTrajectoryAi`（`db.ts:721/742`）：本地读改写放**同一 readwrite 事务**，服务端走字段级 PATCH |

> **加第三条 AI 文本时照抄这套**：加列 → GET 补返回 → PATCH 白名单加一项 → 客户端独立状态机。
> 少任何一步，用户看到的就是"某段解读偶尔消失"。

## D. 构建与配置

### D1. `npm run build` 默认打的是 **React 开发版**

根 `.env` 里有 `NODE_ENV=development`，Vite 会读到它 ⇒ 本地构建产物比线上大 **476KB**。

**任何人拿本地构建数字去优化体积都会得出错误结论。**
要先固定构建模式再比：

```bash
NODE_ENV=production npx vite build --outDir "$TMPDIR/dist-prod"
# 这样出来的产物与线上 SHA-256 逐字节相同
```

> 排查时曾因此误判成「部署漂移」。**哈希/体积不一致只能证明两个产物不同，
> 不能证明哪个更旧。**

### D2. `server/` 不在类型检查范围内

`tsconfig.json` 的 `include` 只有 `src`，且 `exclude` 掉了测试文件。
所以 **`server/` 的 28 个文件完全没有类型检查**，`npm run build` 也不跑 `tsc`。

改服务端代码时，靠 `node --check <file>` 查语法，靠**在服务器上真跑一次**验证行为。

### D3. `public/` 里的东西等于已发布

`public/` 会被原样拷进 `dist/`，`express.static` 与 nginx 都会托管它。
**任何放进 `public/` 的文件都等于已经上线。**

（2026-10-05 已清掉 `design-demo.html` / `demo-yubi-v2.html` 两个设计稿，
`public/` 现在只剩运维用的 `migrate.html`。**别再往里放设计稿或内部页面。**）

### D4. 改报告外观优先去 `report.css`，别在 `index.css` 里找

`src/index.css` 一千八百多行，板块专有类（`rs-` / `tj-` / `ft2-` / `ss-` / `element-`）
与全局基础样式混在一起。
报告级样式已抽到 `src/report/report.css`、打印样式在 `src/report/print.css`——
**改报告外观优先去 `report.css`，不要在 `index.css` 里找。**

## E. React / 交互

### E1. effect 依赖不能传字面量

正则字面量、数组字面量每次渲染都是**新对象**，会让依赖永远失效 →
effect 反复重跑 → `setState` → 无限重渲染。
（曾经让页面滚动被反复打断，排查了很久。）传字符串源，或用 `join('|')` 做 key。

### E2. 目录跳转不能只靠 `<a href="#id">`

URL hash 已是同一个值时浏览器**不会再滚动**，表现是「同一章点第二次没反应」。
要显式按偏移量 `window.scrollTo`。

`scrollIntoView()` 在本项目页面**实测无效**（原因未定），别用它。
